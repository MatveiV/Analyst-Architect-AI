# Техническое задание: система управления страховыми продуктами «СтрахПортал»

## 1. Общие сведения

**Заказчик:** страховая компания «Надёжный Полис», лицензия на осуществление страховой
деятельности (имущественное страхование, ОСАГО, КАСКО, страхование ответственности).

**Проблема:** конфигурация страховых продуктов (тарифы, условия, франшизы) сейчас зашита прямо в
код старой системы — любое изменение тарифа требует релиза с участием разработчиков и занимает
до двух недель. Компания теряет гибкость на конкурентном рынке, где тарифы нужно пересматривать
еженедельно.

**Цель:** создать систему, которая отделяет конфигурацию страховых продуктов от кода — андеррайтер
и продуктовая команда должны иметь возможность настраивать тарифные правила и условия без участия
разработчиков.

## 2. Стейкхолдеры

- **Продуктовая команда** — создаёт и настраивает страховые продукты (правила тарификации,
  франшизы, исключения).
- **Андеррайтеры** — принимают решение по нестандартным заявкам (высокий риск, крупная сумма
  страхования), которые не проходят автоматическую тарификацию.
- **Агенты и брокеры** — оформляют полисы через агентский портал.
- **Отдел урегулирования убытков** — обрабатывает страховые случаи и выплаты.
- **Актуарии** — анализируют убыточность продуктов, готовят рекомендации по пересмотру тарифов.
- **Отдел комплаенс** — следит за соответствием требованиям Банка России как мегарегулятора
  страхового рынка и Закону РФ от 27.11.1992 № 4015-1 «Об организации страхового дела в
  Российской Федерации».

## 3. Функциональные требования

### 3.1 Конструктор страховых продуктов
- Визуальный конструктор тарифных правил: продуктовая команда задаёт факторы риска (возраст,
  стаж вождения, регион, марка автомобиля для автостраховки и т.д.) и коэффициенты к базовому
  тарифу.
- Настройка франшиз: безусловная и условная, фиксированная сумма или процент от страховой суммы.
- Настройка исключений из покрытия (список ситуаций, при которых выплата не производится) —
  текстовые условия, привязанные к продукту, для отображения в полисе.
- Версионирование продукта: изменение тарифа создаёт новую версию, действующие полисы остаются
  на условиях той версии продукта, по которой были оформлены.

### 3.2 Оформление полиса (Quote & Bind)
- Расчёт премии по введённым параметрам риска в реальном времени (движок тарификации применяет
  правила из конструктора продуктов).
- Для ОСАГО — расчёт по коэффициентам, установленным Банком России (базовая ставка, КБМ,
  территориальный коэффициент и т.д. — состав коэффициентов уточняется у актуариев, в этом ТЗ
  не приведён исчерпывающий список).
- Автоматическое одобрение для стандартных случаев (риск-скоринг ниже порога); эскалация
  андеррайтеру для нестандартных.
- Генерация полиса в PDF по шаблону, привязанному к продукту.
- Хранение истории котировок (Quote), даже если клиент не завершил оформление — для последующей
  аналитики конверсии.

### 3.3 Агентский портал
- Личный кабинет агента: список оформленных полисов, комиссионное вознаграждение (расчёт и
  начисление — детали процесса согласовать с финансовым отделом, в этом ТЗ не описаны).
- Возможность оформить полис от имени клиента с автоматическим расчётом агентской комиссии по
  правилам, привязанным к продукту.

### 3.4 Урегулирование убытков
- Регистрация страхового случая: клиент или агент заполняет заявление, прикладывает документы
  (фото, справки, акты).
- Маршрутизация заявления специалисту по урегулированию в зависимости от типа продукта и суммы
  ущерба.
- Расчёт выплаты с учётом франшизы и лимитов покрытия, зафиксированных в полисе на момент
  оформления (а не по текущей версии продукта, если она изменилась).
- Статусы обработки убытка: Зарегистрирован → На рассмотрении → Экспертиза → Одобрен → Выплачен
  → Отказано.
- Учёт сроков рассмотрения — по ОСАГО есть законодательно установленный срок принятия решения
  (уточнить точный срок с комплаенс, в народе — 20 дней, но нужна ссылка на актуальную норму).

### 3.5 Аналитика и отчётность для актуариев
- Отчёт по убыточности продукта: (сумма выплат) / (сумма собранных премий) за период, в разрезе
  продукта и версии тарифа.
- Экспорт данных для актуарных моделей (детальный состав полей уточняется отдельно с актуариями —
  вероятно потребуется отдельная витрина данных).

## 4. Нефункциональные требования

- Расчёт премии по стандартному продукту — не более 1 секунды.
- Доступность агентского портала — не менее 99.5% в рабочее время (09:00–20:00 МСК).
- Персональные данные клиентов и данные о состоянии здоровья (для продуктов страхования жизни,
  если будут добавлены в будущем) — обработка в соответствии с 152-ФЗ, повышенные требования к
  защите специальных категорий персональных данных.
- Полная история изменений тарифных правил (кто, когда, что изменил) — обязательна для аудита
  регулятором.
- Резервное копирование — ежедневное, хранение полисной документации не менее срока, установленного
  внутренним регламентом хранения документов страховой компании (уточнить точный срок).

## 5. Интеграции

- **АИС ОСАГО (Российский союз автостраховщиков)** — обязательная передача данных по договорам
  ОСАГО, протокол и формат определены РСА, интеграция обязательна по закону.
- **Бюро кредитных историй / скоринговые сервисы** — для риск-скоринга нестандартных заявок
  (конкретный поставщик не выбран).
- **Платёжный шлюз** — для оплаты полиса онлайн (эквайринг, поставщик не выбран).
- **1С** — выгрузка бухгалтерских проводок по премиям и выплатам (формат уточняется).
- **СМЭВ / Госуслуги** — опционально, для автоматической проверки документов клиента
  (второй этап, не в текущем объёме).

## 6. Ограничения и допущения

- Первая версия покрывает продукты ОСАГО и КАСКО. Страхование ответственности и другие линии —
  следующие этапы, архитектура должна закладывать расширяемость на новые виды продуктов.
- Мобильное приложение не входит в объём, только веб-версия агентского портала и адаптивная форма
  для оформления полиса на сайте компании.
- Интеграция с АИС ОСАГО — обязательное требование регулятора, приоритет выше остальных
  интеграций.

## 7. Критерии приёмки (черновой набросок)

- Продуктовая команда может создать новый тариф для КАСКО без участия разработчиков.
- Расчёт премии по ОСАГО корректно применяет КБМ клиента.
- Изменение тарифа не затрагивает премию по уже оформленным полисам.
- Заявление на выплату проходит путь от регистрации до решения с фиксацией сроков на каждом шаге.

## 8. Открытые вопросы и риски

- Точный состав коэффициентов ОСАГО и источник их актуальных значений (обновляются Банком России)
  не зафиксирован — критично уточнить перед реализацией тарификации ОСАГО, иначе есть риск
  неверного расчёта премии.
- Законодательный срок рассмотрения заявления по ОСАГО указан ориентировочно («в народе — 20
  дней») — нужна точная ссылка на актуальную редакцию нормативного акта перед реализацией SLA
  в системе.
- Поставщики скоринга и платёжного шлюза не выбраны — риск смещения сроков этих модулей.
- Не описано, что происходит с уже поданными, но не рассмотренными заявлениями на выплату при
  смене версии продукта — открытый вопрос к продуктовой команде.
