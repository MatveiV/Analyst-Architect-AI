# Урок проекта — CRM «Кодформа» (для страницы «Уроки проекта»)

Ниже — готовый набор полей, которые можно скопировать в форму добавления урока
(`POST /lessons` → страница «Уроки проекта»). Даны два примера: один отрицательный (что пошло
не так), один положительный (что сработало хорошо) — чтобы продемонстрировать оба типа `impact_type`.

---

## Пример 1 — отрицательный урок (estimation)

**Название (title):**
Недооценили интеграцию с Jira для учёта часов

**Описание (description):**
На этапе оценки закладывали 16 часов на интеграцию с Jira Cloud API для автоматической выгрузки
отработанных часов. По факту ушло 48 часов — Jira Cloud API оказался с нестандартной пагинацией
и требовал отдельной обработки rate limit (429 ошибки при массовой синхронизации). Обнаружили
проблему только на этапе интеграционного тестирования, за неделю до планового релиза.

**Категория (category):** estimation

**Тип влияния (impact_type):** negative

**Первопричина (root_cause):**
Аналитик оценивал интеграцию по документации без пилотного вызова API — реальные ограничения
(rate limit, формат пагинации) выяснились только в момент написания кода.

**Рекомендация (recommendation):**
Для любой внешней интеграции с незнакомым API закладывать в оценку минимум 4 часа на пилотный
«hello world» вызов реального API ДО финальной оценки трудоёмкости, а не полагаться только на
документацию поставщика.

---

## Пример 2 — положительный урок (process)

**Название (title):**
Чек-лист передачи лида в проект снял путаницу с командой

**Описание (description):**
После внедрения обязательного чек-листа передачи (см. KB-статью «Правила работы команды») случаи,
когда проект стартовал без назначенного backend-разработчика, сократились с 3 за квартал до нуля.

**Категория (category):** process

**Тип влияния (impact_type):** positive

**Рекомендация (recommendation):**
Использовать этот же паттерн (обязательный чек-лист на границе между отделами) для передачи
проекта от PM к отделу поддержки после релиза.
