# Техническое задание: CRM для управления заказами на разработку приложений и информационных систем

## 1. Общие сведения

**Заказчик:** студия заказной разработки ПО «Кодформа» (штат: 35 человек — 22 разработчика, 4 аналитика,
3 менеджера проектов, 2 продавца, 4 административного персонала).

**Проблема:** сейчас заявки от клиентов ведутся в перемешку — часть в Trello, часть в почте, часть
в личных заметках менеджеров. Из-за этого регулярно теряются заявки, дублируется работа по оценке
одного и того же проекта разными аналитиками, нет единой картины загрузки разработчиков по проектам,
счета выставляются с опозданием.

**Цель:** внедрить единую CRM, которая закроет весь цикл — от первого обращения клиента до закрытия
контракта и постпродажного сопровождения.

## 2. Стейкхолдеры

- **Продавцы (Sales)** — заводят лиды, ведут переговоры, готовят коммерческие предложения.
- **Аналитики** — оценивают трудоёмкость по лиду, готовят ТЗ, участвуют в приёмке.
- **Менеджеры проектов (PM)** — ведут проект после подписания контракта, распределяют задачи,
  следят за сроками и бюджетом.
- **Разработчики** — видят свою загрузку и текущие задачи (интеграция с таск-трекером, не полноценный
  функционал CRM).
- **Финансовый отдел** — выставляет счета, следит за оплатами, готовит отчётность.
- **Руководитель студии** — смотрит сводные отчёты: воронка продаж, загрузка команды, маржинальность
  проектов.

## 3. Функциональные требования

### 3.1 Управление лидами и воронкой продаж
- Приём заявок с сайта (веб-форма), из почты (пересылка на выделенный адрес) и вручную.
- Карточка лида: контактные данные, источник, описание задачи клиента, приложенные файлы (бриф,
  примеры ТЗ от клиента).
- Канбан-доска стадий воронки: Новый → Квалификация → Оценка аналитиком → КП отправлено →
  Переговоры → Контракт подписан → Проигран.
- Возможность назначить лид на конкретного продавца и аналитика.
- Автоматическое напоминание продавцу, если лид не двигался по воронке больше 5 рабочих дней.

### 3.2 Оценка и коммерческие предложения
- Форма быстрой оценки: аналитик указывает ориентировочные часы по ролям (Backend/Frontend/QA/
  DevOps/Аналитик) и почасовые ставки — система считает итоговую стоимость и срок.
- Генерация КП в PDF по шаблону компании (логотип, реквизиты, состав команды, этапы, стоимость).
- История версий КП по одному лиду (клиент часто просит скорректировать смету несколько раз).

### 3.3 Проекты и контракты
- При переводе лида в статус «Контракт подписан» — автоматическое создание карточки проекта.
- Карточка проекта: связанный контракт (номер, дата, сумма, файл скана), команда (роли и ФИО),
  этапы (Milestones) со сроками и суммами оплаты по этапу.
- Статусы проекта: Активен, На паузе, Завершён, Расторгнут.
- Учёт фактически отработанных часов по проекту (ручной ввод менеджером или интеграция с
  таск-трекером — см. интеграции).

### 3.4 Финансы
- Выставление счетов по этапам (Milestone) — автоматическая генерация счёта при переводе этапа
  в статус «Готов к оплате».
- Отслеживание статуса оплаты счетов: Выставлен, Оплачен частично, Оплачен, Просрочен.
- Отчёт по дебиторской задолженности — какие клиенты должны и сколько дней просрочки.
- Расчёт маржинальности проекта: (сумма контракта) − (себестоимость по ставкам сотрудников за
  отработанные часы).

### 3.5 Коммуникации
- Единая лента переписки по лиду/проекту: письма, звонки (ручная фиксация), встречи.
- Интеграция с почтой (минимум — пересылка писем в карточку по уникальному адресу вида
  lead-1234@crm.kodforma.ru).

### 3.6 Отчётность
- Дашборд руководителя: воронка продаж по стадиям, сумма контрактов в работе, загрузка команды
  по неделям, топ-5 просроченных счетов.
- Экспорт отчётов в Excel.

## 4. Нефункциональные требования

- Веб-приложение, доступ через браузер (Chrome/Firefox последних двух версий).
- Одновременная работа до 40 пользователей без деградации отклика (целевое время ответа страницы
  — не более 2 секунд на 95-м перцентиле).
- Ролевая модель доступа: Продавец видит только свои лиды, PM — свои проекты, руководитель — всё,
  финансист — все счета и контракты, но не переписку с клиентами.
- Резервное копирование базы данных не реже раза в сутки, хранение бэкапов 30 дней.
- Аудит действий: кто и когда менял стадию лида/статус счёта — хранить историю изменений.

## 5. Интеграции

- **Почта** — приём и отправка через SMTP/IMAP (или Gmail API, если удастся согласовать с клиентом
  переход на Google Workspace).
- **Таск-трекер** — сейчас разработчики используют Jira, желательно подтягивать фактически
  отработанные часы по задачам проекта автоматически (детали интеграции не проработаны, обсудить
  с командой разработки Jira Cloud API).
- **1С-Бухгалтерия** — для выгрузки выставленных счетов (формат обмена уточнить у бухгалтерии,
  скорее всего понадобится CommerceML или ручной экспорт в CSV на первом этапе).
- **Telegram** — уведомления менеджерам о новых лидах и просроченных задачах (опционально,
  можно вторым этапом).

## 6. Ограничения и допущения

- Бюджет проекта — ориентировочно 2,5–3 млн ₽, срок — 4 месяца до запуска MVP.
- Хостинг — на серверах студии (свой VPS), выхода в облако (AWS/Yandex Cloud) не требуется на
  старте, но архитектура не должна это исключать в будущем.
- Мобильного приложения не требуется, только адаптивная вёрстка для планшетов (менеджеры иногда
  работают с iPad на встречах у клиента).
- Интеграция с 1С обсуждалась только устно с бухгалтерией, формальных требований от них пока нет —
  зафиксировать как открытый вопрос.

## 7. Критерии приёмки (черновой набросок, не финализирован)

- Лид проходит весь путь по воронке без ручных манипуляций с базой данных.
- КП генерируется в PDF за один клик.
- Счёт по этапу проекта выставляется автоматически.
- Отчёт по загрузке команды доступен руководителю за произвольный период.

## 8. Открытые вопросы к заказчику

- Нужна ли многовалютность (часть клиентов — из Казахстана и рассчитывается в тенге)?
- Кто именно администрирует ролевую модель — есть ли выделенный администратор CRM или это
  обязанность руководителя студии?
- Требуется ли электронная подпись контрактов внутри системы или подписание остаётся оффлайн?
