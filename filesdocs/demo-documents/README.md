# Демонстрационные документы — Analyst-Architect-AI

Три комплекта документов (по одному на тему), каждый закрывает практически весь функционал
приложения — от загрузки ТЗ до генерации диаграмм, экономики и базы знаний команды. Все файлы —
`.md`, готовы к копированию в соответствующие поля веб-панели.

**Темы:**
1. `01-crm-razrabotka/` — CRM для заказов на разработку приложений/ИС
2. `02-trading-platform/` — торговая платформа для финансовых инструментов
3. `03-insurance/` — система управления страховыми продуктами

Внутри каждой темы — одинаковый набор из 6 файлов:

| Файл | Куда загружать | Что демонстрирует |
|---|---|---|
| `01_TZ_polnoe.md` | **Документы** → «Добавить документ» (title = название темы, text = содержимое файла) | Полноценное ТЗ для рецензии, ArchStudio (URS/SRS/диаграммы/ADR/API), Economics |
| `02_TZ_syroe_dlya_review.md` | **Документы** или сразу **Пакетная рецензия** | Короткое/противоречивое ТЗ — специально, чтобы получить `needs_review=true` и увидеть, как система честно распознаёт пробелы/противоречия |
| `03_KB_pravila_komandy.md` | **База знаний** → «Добавить документ» | Статья базы знаний команды — материал для поиска через `/kb/ask` |
| `04_KB_chastye_voprosy.md` | **База знаний** | То же — увеличивает базу для гибридного поиска |
| `05_KB_slovar_terminov.md` | **База знаний** | То же |
| `06_Urok_proekta.md` | **Уроки проекта** — скопировать поля из markdown в форму (title/description/category/impact_type/root_cause/recommendation) | Два готовых примера (отрицательный и положительный урок) |

## Как пройти по всем страницам приложения (сценарий на одной теме)

Ниже — сквозной сценарий на примере темы 1 (CRM). Для тем 2 и 3 — те же шаги, файлы просто лежат
в соответствующих папках.

### 1. Документы (`/documents`)
Загрузить `01_TZ_polnoe.md` как новый документ (title — «CRM для заказов на разработку», text —
содержимое файла, doc_type — «tz»). Отдельно загрузить `02_TZ_syroe_dlya_review.md` вторым
документом — на нём хорошо видно, как рецензент реагирует на неполноту/противоречия.

### 2. Рецензии (`/reviews`)
Запустить рецензию на обоих документах (`POST /documents/{id}/review`). На «сыром» ТЗ система
должна честно вернуть `needs_review=true` с конкретными вопросами заказчику. На полном ТЗ —
уверенную рецензию с рисками и критериями приёмки. Затем на странице Reviews включить режим
**«🔀 Сравнить рецензии»** и запустить рецензию на полном ТЗ ещё раз — сравнить два прогона
диффом (Фаза 2).

### 3. Пакетная рецензия (`/batch-reviews`)
Загрузить оба ТЗ темы (полное + сырое) одним пакетом — увидеть сводку
«всего/обработано/на проверку/ошибок» и фильтр «только требует проверки» (Фаза 2).

### 4. ArchStudio (`/arch-studio`)
На полном ТЗ (`01_TZ_polnoe.md`):
- Выбрать стандарт требований (например, **ГОСТ 34.602-2020** вместо дефолтного ISO/IEC/IEEE
  29148) и стандарт диаграмм (например, **UML** вместо C4) — сгенерировать URS/SRS и диаграммы,
  увидеть, как меняется структура под выбранный стандарт (Эпик B).
- Открыть вкладку диаграмм, отредактировать код одной диаграммы через встроенный редактор,
  посмотреть историю версий и сделать rollback (Эпик A3).
- Открыть вкладку **«✅ Покрытие»** — увидеть счётчики требований/диаграмм/критериев приёмки
  (Фаза 2).
- Скачать **«📦 Полный пакет»** — DOCX с рецензией и диаграммами-картинками (Эпик A4).
- Сгенерировать ADR (например, решение «свой бэкенд vs no-code CRM-конструктор»).

### 5. Экономика (`/economics`)
Создать build-project на основе документа, запустить декомпозицию задач, рассчитать
CAPEX/OPEX/ROI. Включить чекбокс **«Использовать вместо ползунка»** в блоке «Реальное
использование LLM (30 дней)» — после того, как на предыдущих шагах уже накопились реальные вызовы
LLM, OPEX подставится не вручную, а из фактического расхода токенов (Фаза 3).

### 6. База знаний (`/knowledge-base`)
Загрузить `03_KB_pravila_komandy.md`, `04_KB_chastye_voprosy.md`, `05_KB_slovar_terminov.md`.
Задать вопрос через `/kb/ask`, например: «Что делать, если аналитик оценил проект, а клиент
изменил требования?» — источник должен подтянуться из FAQ. Также обратить внимание: после шагов
3–4 в списке документов базы знаний уже появятся статьи с пометкой **[Авто]** и бейджем `URS`/
`SRS`/`ADR`/`диаграммы` — это автоиндексация сгенерированных артефактов (Фаза 3), которые тоже
участвуют в поиске.

### 7. Уроки проекта (`/lessons`)
Скопировать оба примера из `06_Urok_proekta.md` в форму — они автоматически попадут и в KB
(бейдж `урок`).

### 8. Настройки (`/settings`)
Не требует документов — но стоит показать переключение на провайдер **Ollama** (без API-ключа,
живой список локальных моделей) и бейдж «🔒 Локальный контур», чтобы продемонстрировать Эпик C.

### 9. Аудит (`/audit`) и Дашборд (`/dashboard`)
Не требуют загрузки — сюда стоит зайти после шагов 1–7, чтобы показать: журнал всех запусков с
`provider_used`/`is_local_provider`, разбивку `stats-by-provider` (Эпик C6) и
`actual-usage` (Фаза 3).

## Почему в каждой теме два ТЗ, а не одно

Второй, «сырой» вариант (`02_TZ_syroe_dlya_review.md`) сделан специально коротким и — в теме
2 (торговая платформа) — с явным внутренним противоречием («без плеча» vs «нужен Margin Call»).
Это не ошибка составления: цель — показать на демо, что система **не делает вид, что уверена**,
когда данных не хватает или требования противоречат друг другу, а честно ставит `needs_review=true`
и объясняет причину. Это ключевое требование ко всем вариантам курсового проекта (см.
`Выпускной_проект_по_вайб_кодингу.md`) и одновременно хорошая демонстрация for защиты.

## Соответствие тем реальным доменам

- **CRM для заказов на разработку** — типичный B2B-процесс студии заказной разработки: воронка
  продаж → оценка → контракт → проект → счета. Хорошо показывает URS/SRS с ролями и
  C4-диаграммы (Context/Container) для классического CRUD+workflow приложения.
- **Торговая платформа** — финтех-домен с реальными терминами (FIX-протокол, стакан, Margin
  Call, KYC/AML), пересекается с профессиональным бэкграундом в трейдинговых платформах
  (ThinkOrSwim, DXtrade, QUIK). Хорошо показывает риски и нефункциональные требования
  (latency, доступность) — сильная демонстрация ИИ-рецензента.
- **Страховые продукты** — регуляторный домен (Банк России, РСА, 4015-1, 152-ФЗ) с явными
  открытыми вопросами к комплаенс. Хорошо показывает выбор стандарта **ГОСТ 34** (часто
  требуется у регулируемых заказчиков) и работу с версионированием бизнес-правил.
